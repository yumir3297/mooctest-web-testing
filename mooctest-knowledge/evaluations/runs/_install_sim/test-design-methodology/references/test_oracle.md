# 预期结果判定规则 v0.2（Canonical）

> 唯一规范来源。`mooctest-knowledge/decision-rules/test_oracle.md` 仅为索引。
> 核心修正（v0.2）：**判据证据强度**与**执行状态**分离保存；无依据项不进入正式用例覆盖率统计。

---

## 0. 两个正交维度（不可混为一谈）

### 0.1 维度一：判据来源（Oracle Type）

| 类型 | 判定条件 | 允许的断言强度 |
|---|---|---|
| `ORACLE-SPEC` | 赛题或需求原文给出了结果/文案/状态 | 精确断言 |
| `ORACLE-DERIVED` | 从明确且可复核的规则链推导，链条每步可指认 | 精确断言 + 推导链 |
| `ORACLE-PARTIAL` | 只有部分性质可验证（范围、格式、内部一致性、不变量） | 仅断言已明确的可验证部分，**不得**声称业务整体通过 |
| `ORACLE-UNKNOWN` | 无可靠判据 | **禁止生成业务断言**，转入观察清单 |

### 0.2 维度二：执行状态（Test Status）

`NOT_RUN` / `PASS` / `FAIL` / `BLOCKED` / `INCONCLUSIVE`

- 生成阶段一律 `NOT_RUN`；未实际运行不得写 `PASS`。
- `INCONCLUSIVE`：已执行但判据不足以下结论（典型为 `ORACLE-PARTIAL` 的部分通过）。
- 平台若定义了不同状态名，需在 `submission_constraints.md` 记录映射关系。

### 0.3 记录字段（每条用例必须有）

```
case_id, requirement_id, oracle_type, source_ref, expected, judge_rule, test_status, evidence_ref
```

## 1. 规则明细

### ORA-01 需求明示型
- **Source**：`[MY] ch2 p.13–14`（用例必须同时给出输入与预期输出）
- **Trigger**：需求含明确输出、提示、状态或跳转目标
- **Decision**：直接取需求语义作为预期；只给"应提示错误"未给文案时降级为"包含性断言"并标 `ORACLE-SPEC(弱)`
- **Validation**：预期中每个值都能指回需求具体位置（`source_ref` 精确到条目）
- **Exceptions**：UI 文案与需求措辞不同但语义等价时按语义判定通过，差异写入备注

### ORA-02 规则推导型
- **Source**：`[MY] ch2 p.13–14`
- **Trigger**：需求给出计算/组合/优先级规则但未给最终值
- **Decision**：逐步推导，每步标注所用规则；口径（舍入、币种、时区、单位）必须写明；出现未定义分支立即停止并转 `ORA-04`
- **Validation**：换人按同一链条复算得同一结果
- **Exceptions**：规则含"约/大概/视情况"时不得推导出精确值

### ORA-03 部分可验证型
- **Source**：`[MY] ch10 p.195–198`（分层结构导致后端不可见）；`[EI] ch5 p.66`（内部一致性）
- **Trigger**：结果依赖数据库写入、第三方接口、异步任务
- **Decision**：拆成"页面可断言"与"页面不可断言"两栏；可断言部分给确定值；不可断言部分写间接验证手段，无手段则标不可验证
- **Output**：`ORACLE-PARTIAL` + 双栏预期 + 明确的检查范围声明
- **Validation**：不得用页面文案推断后端成功；不得声明"业务整体通过"
- **Exceptions**：刷新/重进列表属于**弱验证**，必须标注

### ORA-04 无可靠依据 → 观察项（不计覆盖）
- **Source**：`[MY] ch2 p.13–14`（无预期即非有效测试用例）；`[MY] ch10 p.200`（无规格无法设计合适测试）；`[EI] ch5 p.68`（oracle problem）
- **Trigger**：需求缺失/矛盾/不可实现；依赖未知外部系统
- **Decision**：
  1. **不生成** `expected` 业务值；
  2. 写入 `observations.json`，字段：`obs_id, requirement_id, scenario, observed, why_insufficient, followup`；
  3. 若该场景同时违反底线，转 `ORA-05` 后可生成 `ORACLE-PARTIAL` 用例；
  4. 缺口写入 `coverage_report.json.gaps`。
- **Validation**：正式用例集中 `ORACLE-UNKNOWN` 数量必须为 0；全文检索不得出现"应显示 XX/应成功"等无依据断言
- **Exceptions**：获得补充口径（赛题/需求澄清）后升级为 `ORA-01/02`
- **关键口径**：观察项 **不计入** 可验证用例覆盖率，也 **不得** 用来"凑满"需求覆盖

### ORA-05 Never / Always 底线断言
- **Source**：`[EI] ch5 p.63–65`
- **Trigger**：规格不全但存在业务不可违反的底线
- **Decision**：写"绝不发生"（重复扣款、负金额、越权看到他人数据）与"永远成立"（总额=明细之和、状态单向）；仅这些条目允许在无规格下断言；每条须说明违反后果
- **Exceptions**：把"界面好看""文案友好"写成 Never/Always 属误用，必须剔除

### ORA-06 近似判定
- **Source**：`[EI] ch5 p.68–70`
- **Trigger**：无法得到精确预期但能判断"是否明显不对"
- **Decision**：按优先级取参照——范围 → 特征（格式/单位/排序性）→ 反向操作 → 极端条件
- **Validation**：判定规则可证伪（能说清什么算失败）
- **Exceptions**：资金精算、法定格式不得用近似判定

### ORA-07 替代参照（内部一致性 / 标准 / 可比软件）
- **Source**：`[EI] ch5 p.65–67`
- **Decision**：① 同值多处展示是否一致；② 是否符合公开标准；③ 与同类产品是否明显背离
- **Exceptions**："别家这么做"只能触发疑点，不能当需求依据

### ORA-08 观察 ≠ 缺陷
- **Source**：`[EI] ch5 p.62–63`
- **Decision**：三态——有依据且违反=缺陷；无依据但违反底线=缺陷候选；无依据且不违反底线=疑点

### ORA-09 失败归因与"不得为通过而改预期"（v0.2 新增）
- **Source**：`[ENG]`；与 `[MY] ch2 p.13–14` 一致（预期是先验定义，不随后验调整）
- **Trigger**：任何 `FAIL`
- **Decision**：先归因为四类之一，再决定动作：
  | 归因 | 判据 | 允许的动作 |
  |---|---|---|
  | 业务缺陷 | 有 `SPEC/DERIVED` 依据且实际违反 | 记录缺陷，不改预期 |
  | 脚本错误 | 定位失败、等待不足、数据前置不满足 | 改脚本/等待，不改预期 |
  | 环境错误 | 网络、服务不可用、浏览器版本不符 | 标 `BLOCKED`，重跑 |
  | 规格歧义 | 预期本身无可靠来源 | 转 `ORA-04` 观察项 |
- **禁止**：为了让用例通过而修改 `expected` 或删改用例；修改预期必须附新增需求证据（`source_ref` 变化记录）
- **Validation**：每条 `FAIL` 都有归因标签；预期变更均有证据引用

## 2. 统计口径（双指标，v0.2 新增）

| 指标 | 公式 | 说明 |
|---|---|---|
| 需求关联度 | 已有用例关联的 `可测` 需求数 ÷ `可测` 需求总数 | 只说明"提到过"，不代表可判定 |
| 可验证用例覆盖率 | 拥有 `SPEC/DERIVED/PARTIAL` 判据的用例所覆盖的 `可测` 需求数 ÷ `可测` 需求总数 | **对外汇报的主指标** |
| 观察项数 | `observations.json` 条目数 | 单列，不并入覆盖率 |
| 虚构预期数 | 无 `source_ref` 却被写成确定值的用例数 | 必须为 0 |

禁止使用"用例总数/需求总数"作为覆盖率。

---

## 3. 输出契约（分阶段，v0.2 减负）

- **设计阶段**：完整字段，写入 `cases.json`（机器）+ Markdown 表格（人读）。
- **审查阶段**：只输出差异、发现、建议，不重复整张表。
- **最终交付**：由编排层统一生成 Excel，本 Skill 不直接产出交付文档。

---

## 4. 明确禁止

1. 为凑完整而补写需求中不存在的业务规则。
2. 用"系统应该会……"作为预期依据。
3. 把外部系统返回值（运费、时效、距离）写成确定值。
4. 把经验惯例写成 `ORACLE-SPEC`。
5. 用 PASS/FAIL 二元结论覆盖"只能观察"的场景。
6. 生成阶段写 `PASS`。
