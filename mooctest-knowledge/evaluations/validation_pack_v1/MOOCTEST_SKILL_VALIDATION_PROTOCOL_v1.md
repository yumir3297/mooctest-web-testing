# Mooctest 测试设计 Skill 验收方案 v1.0

状态：赛前知识工程阶段的评测协议。**不是官方比赛评分标准**，也不代表完成实际评测。

适用材料：Myers《The Art of Software Testing》3rd ed.、Hendrickson《Explore It!》及 Trae 提炼的 `test-design-methodology`。

## 0. 三种证据级别

- S（静态检查）：SKILL.md / 规则文件 / 参考路径 / 来源标注；不能证明模型会执行。
- B（行为评测）：相同模型在隔离的虚构需求集上实际生成用例；可以判断规则服从、正确性与性能差异。
- E（端到端）：真实练习题 + 浏览器 + Selenium 运行日志 + 证据截图；尚未进入此阶段。

任何结论都须附：样本 ID、输入、实际 Agent 输出文件、评审结果、运行配置；没有实际记录就写“未验证”。

## 1. 赛前材料验收 S

1. 核查原始来源：书名/版次/章节/页码、规则出处是否准确；对未提供的教材正文及 references 必须记“未验证”，不得推测。
2. frontmatter 结构、技能名称、适用及禁用边界。
3. 规则矛盾：例如“每边界4点”对离散/连续或精度不同场景的错误；“参数>=4优先判定表”对独立参数的错误。
4. 交接契约：输入需求 ID、用例 ID、需求依据、oracle 类型、判定条件、证据可追溯。
5. 路径：复制整个 Skill 到候选安装路径后，在受控环境确认 references 均能实际打开；只拿入口文件不能判通过。
6. 时间与上下文：每次加载的文件列表、Token 占用；Token 估算仅供规划，实测需由运行环境计量。

**S 阶段阻断项**：伪造教材来源；错误的硬规则仍被强制执行；引用文件缺失却声称加载成功；把示例业务数据当作赛题要求。

## 2. 行为测试 B：八个隔离题

题目以 `MOOCTEST_SKILL_TEST_FIXTURES_v1.json` 为准，每次独立新会话运行，不能把期望检查项目作为提示输入。测试输入均为教学编造的需求，与顺丰或慕测真实题目无关。

- T01 整数边界：重量仅允许整数 kg，范围闭区间[1,20]；应覆盖合法上下界与相邻非法值，不能强制 0.01 小数。
- T02 小数边界：0<w<=20，精度0.1kg；应正确处理排除0、包含20和精度。不应硬性生成“四点”或用不允许的精度。
- T03 四参数非条件：四字段与必填/可选约束，无参数间的业务决策关系；不能仅因参数>=4而强制判定表。
- T04 真正决策表：企业且已支付时才显示“申请发票”，否则隐藏；必须覆盖四种逻辑组合，明确 oracle 来自需求。
- T05 状态与重复提交：提交后只能产生一条记录，重复点击不得重复创建；应验证状态/副作用，且不得无证据宣称执行。
- T06 未指定金额：系统显示运费报价但未给计算公式；可验证是否展示，不能断言具体金额或自行编造费率。
- T07 赛题限制：只要求给定四组城市组合、且禁止额外组合；不得扩张正式用例范围。
- T08 未探索网页：只给功能文字，未给 DOM 或可访问页面；不得编造 CSS/XPath、执行状态、截图文件。

每题要求输出 JSON 或结构化 Markdown：需求 ID、方法选择及理由、候选测试用例、测试预言类型与证据、无法确定的信息、审查结果。为了检验是否遵循材料，要求记录实际加载的 Skill/参考文件及工具调用情况（如有），不得伪造。

## 3. 可复现 A/B 协议

- A：同一模型、不启用新 `test-design-methodology`，仍可以使用同样固定的基础技能。
- B：同一模型、同样基础技能，另加载新 `test-design-methodology` 及其按需 references。
- 两组使用完全相同的八个输入题，但不同独立会话；各题各组建议3次运行；模型、版本、参数、提示、可用工具、文件权限一致。
- 由评审者尽量盲评 A/B 输出；不得将评审答案注入被测提示。记录模型版本、提示哈希、Skill 版本、加载文件、输入/输出 Token、耗时和错误类型。
- 不把本测试集当作唯一迭代目标；修改规则后，用留出的真实历史题验证泛化，防止过拟合。

## 4. 行为评分（本项目自设，不是官方评分）

每题 10 分，总分80分：
- 需求约束忠实度（0–3）：包含/排除边界、精度、限定输入、状态等是否正确。
- 方法选择正确性（0–2）：符合需求条件，避免形式主义与重复。
- Oracle 依据（0–2）：预期来自规格/可靠推导；不编造价格、元素、反馈文案。
- 可追溯与可执行设计（0–2）：目的、数据、操作、判定条件、需求 ID 清楚。
- 经济性（0–1）：无明显多余或重复用例，不因模板生成低价值用例。

**硬门禁（出现任一项则该题不通过，不能用总分掩盖）**：
- 伪造了需求中没有的可验证业务规则，并作为确定正确的预期。
- 违反题目明确限定的数据或操作范围。
- 没有浏览器运行证据却声称脚本/用例已执行或截图已生成。

**建议的内部验收目标**（可调整，不是已测数据）：
- 新 Skill 在8题中不出现任何硬门禁错误；如出现先修错误而非追求分数。
- 修订后 B 的平均评分高于或至少不低于 A，并且不得在 oracle 准确性方面退化。
- B 所增加的 Token/耗时与质量收益需同时报告，不预设“更长必然更好”。

## 5. 真实赛题 E 阶段（后续）

取得真实、可合法练习的顺丰等题目后，固定题目、浏览器与运行环境，比较 A/B 在：需求项覆盖、有效用例率、有效断言比例、Selenium 脚本运行结果、失败诊断、截图真实对应性、交付完整率、耗时、Token 等指标上的表现。脚本通过只说明执行条件满足，不直接等于发现更多软件缺陷。正式比赛是否可用 AI 必须另核当届规则。

## 6. 交给 Trae 的任务

请使用本协议与 JSON 试题，先修正规则并作**材料阶段验收**；把每题原始输入、未经润色的模型输出、评分、错误原因、Skill版本及运行日志存放到 `evaluations/runs/`，生成 `VALIDATION_RESULTS.md`。如果当前 Trae 环境不能启动隔离对话或统计 Token，明确标记阻塞，不得编造实验。先独立构建候选“金标准检查表”，再运行模型；不能将金标准检查表注入被测会话。最后只汇报已验证的结论。
