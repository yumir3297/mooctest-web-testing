# 运行时调用试验：`test-design-methodology` 对测试设计产出的影响（2026-10-31）

## 1. 目的与边界

验证已安装的 `.opencode/skills/test-design-methodology/` 在被加载后，是否改变**同一份需求**的测试设计产出，并把差异变成可清点的数字。

本试验只做**设计**，不做浏览器执行：所有用例 `test_status = NOT_RUN`，不声称任何业务通过或失败。

## 2. 试验设置

| 项 | 值 |
|---|---|
| 日期 | 2026-10-31 |
| 执行者 | 单个 Agent 会话（DeepSeek V4.1 Flash），非独立进程 |
| A 组 | 不加载 Skill，按常识直接列用例 |

| 需求 | 同一份，逐字固定（见 §3），两组均不得修改 |
| 执行次数 | 每组 1 次 |
| 盲评 | **否**：同一会话先做 A 后做 B，B 可能受 A 影响 |

## 3. 固定需求（不得修改）

一个「优惠券结算」表单：

- 字段：订单金额（整数，单位元，范围 1–9999）、优惠券码（6 位大写字母数字，必须以 `CP` 开头）、会员等级（普通/银卡/金卡）、是否叠加积分（是/否）。
- 业务规则：
  1. 金卡且订单金额 ≥ 500 可用 9 折券；
  2. 银卡 ≥ 800 可用 8.5 折；
  3. 普通会员不可用折扣券；
  4. 积分叠加时折扣后金额再减 1 元且不低于 0；
  5. 优惠券码非法时给出错误提示且不改变金额。

## 7. 结论

**提升在哪**

1. **分诊先做**：B 组先把 4 条歧义需求挡在正式用例之外（R-14…R-17），A 组则用"正常"或猜测把它们混进用例（A-16）。
2. **不可判定预期归零**：A 组 3 条"正常/正常显示"，B 组 0 条；对应地，可验证需求覆盖从 9/13 提到 13/13。
3. **无效分区成体系**：A 组 9/13，且把两个非法条件混在一条（A-14）；B 组 13/13，每种非法格式独立一条（MS-02）。
4. **判定表可复核**：B 组 8 条可达规则全部命中，并显式标注 2 列"不适用"；A 组没有规则层，边界值是否命中规则列无法核对。
5. **重复受控**：A 组 1 条重复（0 与 −5），B 组 0 条。

**没有提升在哪**

1. **用例数没有变少**：B 组 24 条 > A 组 16 条。原因是 B 组把 13 个无效分区和 12 个边界项拆开，而不是"更精简"。
2. **边界命中只从 9 提到 10**：A 组碰巧也打到了 501，只是预期不可判定；B 组反而因取整口径缺失，**主动放弃** 501/801 两条边界。原始取值覆盖不等于可验证覆盖。
3. **发现不了需求本身的缺口**：R-14 的取整、R-16 的积分前提，B 组只能登记，不能解决；这部分要靠需求澄清。
4. **不产生脚本**：两组都不产出 Selenium 代码，执行覆盖率无法从本次试验得出。

## 8. 局限

- **单次**：每组仅 1 次，无重复运行，不能排除偶然性。
- **非盲评**：同一会话先 A 后 B，B 组见过 A 组的输出，存在污染。
- **非真实赛题**：需求自造，不含官方评分维度与权重，结论不能外推到比赛得分。
- **无真实页面**：控件类型、提示文案、取整实现均未知，B 组对"可输入小数/负数"作了显式假设；真实页面若阻止输入，AIP-02/AIP-04 应改记 N/A。
- **无执行**：所有用例 `NOT_RUN`，本试验不证明任何产品缺陷。
