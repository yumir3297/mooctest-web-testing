## 1. 对两本教材的核心价值判断

| 教材 | 我的判断 | 依据 |
|---|---|---|
| The Art of Software Testing, 3rd ed. | **最高价值在 ch4 的"策略"而非"技术"**。单看等价类/边界值只是概念；ch4 p.82–83 的五步组合顺序才是可被 Agent 执行的调度算法。ch2 的四条原则（预期输出必填、无效输入优先、检查副作用、缺陷聚集）是判定基线的来源。 | p.41–84 精读；p.5–18 精读 |
| Explore It! | **唯一能覆盖"无规格"场景的材料**。Never/Always、内部一致性、标准、可比软件、近似判定构成四层替代 oracle；charter 提供了时间盒探索的可操作单元。但它对"如何产出可交付用例"着墨少，不能承担主设计职责。 | ch5 p.63–70；ch2 p.29–32；A2 p.161–166 |
| Introduction to Software Testing, 2nd ed. | **项目中不存在**，无法评价。其缺口导致覆盖准则与组合测试只能降级引用 ISTQB 与工程经验。 | 见 `inventory/source_registry.md` §3 |

一句话：Myers 管"怎么设计"，Explore It 管"没规格时怎么判"，两者不可互换。

## 3. 知识库架构

```
mooctest-knowledge/
├── sources/chapter-text/         # 15 个按章切分文本，带页码锚点（只读派生，可删）

│   ├── method_selector.md        # 10 条 MS 规则 + 矩阵 + 冲突分析 + 停止条件
│   ├── test_oracle.md            # 8 条 ORA 规则 + 输出契约
│   ├── coverage_review.md        # 9 条 REV 规则 + 自评模板
│   └── defect_discovery.md       # 10 条 DEF 规则 + Web 勾选清单
├── examples/web_test_scenarios.md# 6 场景（全部标注【假设】，未执行）
```

## 4. 我认为当前方案的不足

1. **权威性缺口**：`pairwise`、组合降级策略无教材出处；若评审要求"每条规则都能溯源"，这 6 条会被扣分。
2. **规则密度偏高**：37 条规则对一次比赛任务可能过重，尤其 MS-05/REV-03/REV-05 属"锦上添花"。
3. **缺少真实需求验证**：所有示例都是自拟假设，无法证明规则在真实赛题下不产生冲突。
4. **Web 特化不足**：DEF-06/07/09 主要靠工程经验，Myers ch10 只给分层框架，Explore It 的 Web 启发式只有两条。
5. **未与现有 5 个 Skill 实际对接**：接口（输入/输出契约）只是纸面约定，未做过一次真实串联。
6. **度量缺失**：没有可运行的自动评分脚本，"覆盖率"仍需人工核对矩阵。
7. **2026 规则未知**：默认优先级建立在 2025 评分维度上。

## 5. 可能冲突与 Token 成本

| 冲突/成本点 | 描述 | 当前处置 |
|---|---|---|
| MS-03 vs MS-05 | 判定表已压缩组合，成对覆盖可能重复计数 | 明确"有业务规则归判定表，成对只处理自由参数" |
| ORA-05 vs REV-04 | 无规格断言在 ORA 允许、在 REV 可能被判"无依据" | 规定 ORA-05 必须附"违反后果"，REV-04 对其豁免 |
| REV-02 vs MS-09 | 方法覆盖要求与"适度停止"可能矛盾 | 停止条件以 REV 为准，MS-09 只排序不删减 |
| 全量加载 | 4 个规则文件 + 方法论 ≈ 6k–7k tokens | 建议按需加载（见 `USAGE_GUIDE_DRAFT.md`） |
| 示例污染 | `examples/` 含具体费率，可能被模型当成需求 | 已在文件头与 references 中双重警告 |
| 教材文本 | `sources/` 体量大 | 默认不加载，仅在核对出处时按页检索 |

Token 估算（中文按字符近似）：`method_selector` ~1.5k、`test_oracle` ~1.2k、`coverage_review` ~1.2k、`defect_discovery` ~1.4k、方法论 ~1.3k、SKILL ~1.5k。全量 ≈ 6.7k。

## 6. Skill 数量与粒度建议

我的建议：**保持 1 个新 Skill，不拆分**。

理由：
- 现有 5 个 Skill 已覆盖"拆需求（breakdown-test）→ 写用例（test-case-writing）→ 评审（test-case-reviewer）→ 探索（playwright-cli）→ 工程化（ui-test-selenium）"。本 Skill 的独特价值是**"需求解析 + 方法选择 + oracle 判定"**这一段，恰好是现有链路中空着的。
- 拆成 3 个（需求分析 / 方法选择 / oracle）会造成每个 Skill 都要重复加载同一套术语，反而提高总 token。
- 若必须拆，建议只拆出 `test-oracle`（因为它可被 review 与脚本断言复用），其余留在主 Skill。

粒度上，SKILL.md 只保留五步流程 + 禁令 + 输出契约；所有表格留在 `decision-rules/`。当前草案已按此执行。

## 7. 需要进一步讨论的技术决策问题

**Q1. "无依据预期"该不该保留在正式用例集中？**
A 方案：降级为"观察项"，单独成表，不计入用例覆盖率。
B 方案：仍作为用例，但预期字段写"观察 + 失败条件"，计入覆盖率。
我倾向 A（更符合评分中的"规范性"），但会让用例数变少，可能影响"充分性"。请评审者判断。

**Q2. 组合测试没有权威出处时，是否应当从规则库中移除？**
保留（标 `[工程经验/待验证]`）可覆盖评分要求的"组合测试"；移除则规则库更"干净"但少一项评分抓手。

**Q3. 探索式测试在正式比赛中应占多大比重？**
比赛是限时、限交付物、要截图取证的。探索产出难以直接变成"用例文档 + 脚本"。是否应把 Explore It 只用于 oracle 与风险发现，不引入 charter 流程？

**Q4. 规则数量与服从度如何权衡？**
37 条规则可能导致模型"看起来遵守但实际漏项"。是否应压缩到"15 条核心 + 22 条附录"？

**Q5. 与 `knowledge/08_derived_rules/` 旧规则的双份口径如何处理？**
合并（保留一份）、还是分层（新库为方法论、旧文件为速查）？当前采用分层，存在漂移风险。

## 8. 建议方案及理由

1. **先做"最小可用规则集"**：MS-01/02/03/04、ORA-01..04、REV-01/02/04、DEF-03/04/07/10，共 15 条。理由是它们直接对应评分维度且互相不冲突。
2. **Skill 保持单个数目**，SKILL.md 承载五步流程，其余按需加载。
3. **oracle 独立成文件而不独立成 Skill**，保留未来被脚本断言复用的可能。
4. **示例集只保留 3 个**（边界、决策表、无规格），另 3 个移入附录，降低污染风险。
5. **在真实赛题到手后做一次 A/B**，用 `evaluation_plan.md` 的评分表，而不是凭感觉判断规则有效。
6. **暂不安装 Skill、暂不接入 OpenCode**，等外部评审与真实需求验证后再定稿。

请评审者优先回答 Q1、Q3、Q4——这三项决定知识库的最终形态。
