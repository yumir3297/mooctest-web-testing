## 1. ID 命名规范（全局唯一、可正则校验）

| 类型 | 格式 | 正则 | 示例 |
|---|---|---|---|
| 需求点 | `REQ-{序号2位}` | `^REQ-\d{2}$` | `REQ-03` |
| 测试用例 | `TC-WEB-{序号3位}` | `^TC-WEB-\d{3}$` | `TC-WEB-012` |
| 测试代码（函数/方法） | `test_{TC_ID}_{简短描述}` | `^test_TC-WEB-\d{3}_[a-z0-9_]+$` | `test_TC-WEB-012_submit_invalid_phone` |
| 执行记录 | `RUN-{日期8位}-{序号2位}` | `^RUN-\d{8}-\d{2}$` | `RUN-20261101-01` |
| 截图 | `SHOT-{TC_ID}-{序号2位}-{状态}` | `^SHOT-TC-WEB-\d{3}-\d{2}-(PASS|FAIL|STEP)$` | `SHOT-TC-WEB-012-01-PASS.png` |
| 缺陷（可选） | `BUG-{序号3位}` | `^BUG-\d{3}$` | `BUG-004` |

**规则**
1. 用例 ID 一经分配不复用、不重排；删除用例时保留空号并记录原因。
2. 一个用例 ID 只对应一个测试函数；一个测试函数只覆盖一个用例 ID。
3. 截图必须带用例 ID，禁止出现无归属的 `screenshot1.png`。

## 2. 五层映射关系（唯一事实链）

```
REQ-xx  ──1:n──▶  TC-WEB-xxx  ──1:1──▶  test_TC-WEB-xxx_yyy
                        │                        │
                        └────1:n──▶ SHOT-TC-WEB-xxx-zz   ◀── RUN-yyyymmdd-xx
```

四条强制约束：

1. **需求 → 用例**：每个 `REQ-xx` 至少 1 条用例；每条用例至少回指 1 个 `REQ-xx`。
2. **用例 → 代码**：用例表中的「自动化脚本」列必须写出函数名，且函数名包含用例 ID。
3. **代码 → 结果**：执行记录按用例 ID 汇总 PASS/FAIL/SKIP 与失败分类码。
4. **结果 → 截图**：每条用例至少 1 张关键步骤截图；FAIL 用例必须有失败现场截图。

未满足任一条 → 提交物判为「不一致」，需在交付前修复。

依据：`[S-01]` 代码-用例一致性、截图要求；`[S-03]` ISO/IEC/IEEE 29119-3 公开摘要中的测试文档可追溯原则；`[S-02]` ISTQB 测试依据—测试件可追溯性。

## 3. 测试用例表列定义（Excel / CSV 通用）

| 列名 | 必填 | 说明 | 校验规则 |
|---|---|---|---|
| 用例ID | 是 | `TC-WEB-xxx` | 唯一、匹配正则 |
| 需求ID | 是 | `REQ-xx`，多条用 `;` 分隔 | 每个 ID 必须存在于需求表 |
| 模块/功能点 | 是 | 页面或功能名 | 非空 |
| 用例标题 | 是 | 一句话说明测什么 | ≤ 60 字、不含「测试」空话 |
| 优先级 | 是 | P0/P1/P2/P3 | 枚举值 |
| 用例类型 | 是 | 正向/异常/边界/状态/组合/非功能 | 枚举值 |
| 设计方法 | 是 | 等价类/边界值/决策表/状态迁移/组合/错误推测 | 枚举值，与用例类型自洽 |
| 前置条件 | 是 | 登录态、角色、数据初态 | 非空；缺项须标「假设:」 |
| 测试数据 | 是 | 具体值或 `${占位符}` | 与步骤一一对应 |
| 测试步骤 | 是 | 编号步骤，每步一个动作 | ≥ 1 步，无「相关页面」等模糊动作 |
| 预期结果 | 是 | 可观测、可判定 | 禁用「正常」「成功」等不可判定词 |
| 自动化脚本 | 否/是* | `test_TC-WEB-xxx_yyy` | 有代码的用例必填；无代码须在备注写原因 |
| 执行结果 | 否 | PASS/FAIL/SKIP（由执行回填） | 与执行记录一致 |
| 失败分类 | 否 | `ENV/LOCATOR/TIMING/DATA/SCRIPT/APP/ASSERT` | FAIL 时必填 |
| 截图文件 | 否/是* | `SHOT-...png;...` | 每用例 ≥1 张 |
| 备注 | 否 | 假设、缺口、限制 | 缺口必须有 |

\* 交付前必须满足：有代码 ↔ 有截图 ↔ 有执行结果，三者同源。

## 4. 目录与文件布局（交付物）

```
submission/
  README.md                     # 运行方式、依赖版本、目录说明
  requirements.txt              # 锁版本（selenium==4.51.0, pytest==9.1.1 ...）
  test_cases/
    test_cases.xlsx             # 用例表（列定义见 §3）
    test_cases.csv              # 同上机器可读副本（便于自动校验）
  tests/
    conftest.py                 # driver fixture、失败截图钩子
    pages/                      # Page Object
    test_web_*.py               # 测试函数，命名含 TC ID
  data/
    *.yaml|*.csv                # 测试数据
  artifacts/
    RUN-20261101-01/
      run_log.txt
      results.csv               # TC_ID,status,error_code,duration,start
      screenshots/              # SHOT-*.png
      page_sources/             # 失败页 HTML
  docs/
    requirement_trace.csv       # REQ-xx 与用例的对应表
```

## 5. 截图规范

1. 命名：`SHOT-TC-WEB-{xxx}-{序号}-{PASS|FAIL|STEP}.png`。
2. 内容：关键步骤与最终结果各至少 1 张；FAIL 必附现场图（含可见报错/异常状态）。
3. 尺寸：整页或关键区域，分辨率 ≥ 1280×720；不做裁切拼接。
4. 元数据：`results.csv` 中记录截图相对路径与所属用例 ID，禁止只放在文件夹里不登记。

依据：`[S-01]`（截图完整性为评分项）、`[S-04]`（Web 赛项需提交「测试用例 + 测试代码 + 截图压缩包」）。

## 6. 自动一致性校验清单（交付前必须全绿）

> ⚠ **未实现（历史设想，2026-10-31 标注）**：本节 10 条校验在本仓库没有对应实现，不得当作已落地门禁。
> 现实实现由质量门禁模块承担（约定路径 `tools/pre_submission_gate.py`；写入本标注时该文件尚未创建）。

| # | 检查 | 失败判定 |
|---|---|---|
| 1 | 用例 ID 唯一且匹配正则 | 重复/格式错 |
| 2 | 每条用例的 `需求ID` 均在需求表存在 | 悬空引用 |
| 3 | 每个 `REQ-xx` 至少被 1 条用例引用 | 需求无覆盖 |
| 4 | 每条「有代码」用例的 `自动化脚本` 函数名在 `tests/` 中真实存在 | 代码-用例不一致 |
| 5 | 每个测试函数名都能反查到一个用例 ID | 代码无归属 |
| 6 | 执行记录中的 TC ID 集合 ⊆ 用例表 ID 集合 | 结果悬空 |
| 7 | 每条用例至少有 1 张 `SHOT-` 截图 | 截图缺失 |
| 8 | FAIL 用例均有失败分类码与失败截图 | 结论不可复核 |
| 9 | 预期结果列无「正常/成功/无异常」等不可判定词 | 可判定性不足 |
| 10 | 缺口清单非空时必须写明原因与影响 | 缺口静默 |

## 7. 与评分维度的对应关系

| 评分维度 | 由本规范保证的机制 |
|---|---|
| 用例充分性 | 需求全覆盖（§2 约束1）+ 类型/方法枚举（§3） |
| 用例可读性 | 字段固定、标题与步骤约束（§3） |
| 用例可复现性 | 前置条件 + 数据 + 步骤分离（§3） |
| 代码-用例一致性 | ID 一一对应 + 自动校验 #4/#5 |
| 截图完整性 | 命名、数量、登记（§5 + #7） |
